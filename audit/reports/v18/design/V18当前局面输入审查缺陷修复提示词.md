## 二、P1 缺陷修复清单

### V18-A1 + V18-A3（一个根因，一个主题）：被鸣舍牌的双重计数与 supplied 失真

- **等级**：P1（语义错误）。
- **位置**：
  - 状态机：`RiichiEnv/riichienv-core/src/state/mod.rs:1204-1219`（Pon/Chi）、
    `riichienv-core/src/state/event_handler.rs:446-494`（apply_log_action ChiPengGang）、
    `event_handler.rs:577-612`（Ankan/Kakan 路径）、`state/mod.rs:1453-1465`（_resolve_kan）；
  - 编码器：`riichienv-python/src/current_state_encoding.rs:327-333`（is_supplied）、
    `current_state_encoding.rs:409-434`（public_counts 区域求和）、
    `current_state_encoding.rs:768-817`（TILE_STATE public/known/unknown）。
- **根因**：状态机把被鸣牌**同时保留在弃牌者牌河与副露**（discards 只 push 不移除、meld.called_tile
  与 river 用同一 TID 值），而编码器把“四家牌河 + 全部副露 + 宝牌指示牌”按**区域出现次数**求和；
  同时 `is_supplied` 只按 `from_who==seat && called_tile==tile` 值匹配，replay 对同牌种复用同一 TID
  （`parse_mjai_tile` 每次新建 TileManager，见 `parser.rs:14-42`），因此同一对手先后舍出两张同牌种、
  仅一张被鸣时**两张都被标 supplied=1**。
- **最小复现**：
  - 真实：`RiichiEnv/tests/data/126_204_0_mjai.jsonl` 记录 2（rec2，对手 Pon E 后任一决策）：
    TILE_STATE kind 27 public=4/known=4/unknown=0/all_seen=1，而实体应为 public=3/known=3/unknown=1；
  - 合成：`v18_audit_oracle.py` §3（p1 河 [E,E,9s]，p2 Pon E(from p1)）→ river marks [(1,1),(2,1),(3,0)]，
    正确应为 [(1,1),(2,0),(3,0)]。
- **影响**：TILE_STATE 的 public/known/unknown/all_seen 失真；`remaining=4-own-public` 低估 1，
  进而 SELF_STATE_ANALYSIS 的 `advance_remaining/wait_remaining` 低估；cap=4 会掩盖第五次错误计数；
  RIVER_DISCARD.supplied 对同牌种多张全标，防守信息错误。
- **修复方案（必须同时完成）**：
  1. `Meld` 增加字段 `called_tile_index: Option<u8>`（或 `i16`，-1 表示 N/A），记录被鸣牌在
     供牌者牌河中的**本地下标**（含 0 基；含 chi/pon/daiminkan，ankan/kakan 为 None）。
     建议 serde 侧加 `#[serde(default)]` 或同步更新全部 JSON 构造点（fixture/合成 Observation），
     避免旧 JSON 反序列化失败；编码数据集/checkpoint 无需向后兼容（旧 V18 视为不兼容）。
     三个设置点都必须写入：`state/mod.rs` 的 Pon/Chi 块（取 `last_discard` 时刻
     `discarder.discards.len()-1`）、`event_handler.rs` 的 `apply_log_action::ChiPengGang`、
     Ankan/Kakan/内部 `_resolve_kan`（daiminkan/kakan 保留原 pon 的被鸣下标）。
     同时同步 `riichienv-core/src/types.rs` 的 Meld 构造器/序列化、`riichi_ppo_v1` 侧无直接依赖时
     仅保持 pyclass getter；`Observation` 的 serde 结构会变化，需更新
     `riichi_ppo_v1/model/bridge.py`/测试中用到的 Meld JSON 构造（若有）。
  2. `current_state_encoding.rs::is_supplied` 改为按 **（from_who, called_tile_index）** 精确匹配：
     遍历每张河牌时应能通过下标集合判断，而不是按 TID 值；标记恰好被鸣的那一张。
  3. `public_counts` 改为**实体去重**：先为每座收集“被鸣下标集合”，计数时跳过这些下标对应的河牌，
     再累加全部副露牌与宝牌指示牌（被鸣牌只出现在副露里一次）。
  4. TILE_STATE 的 public/known/unknown 随之恢复为实体口径；`remaining_counts` 输入用实体口径。
  5. RIVER_DISCARD.supplied 编码该精确下标命中；age/river_index/riichi_stage 不受影响。
- **回归测试**：
  - Rust 单测：构造“同牌种两张河牌只一张被鸣”的 Meld + discards，断言 is_supplied 只标一张、
    public_counts 实体数正确（含 cap 不再掩盖：river 2×E + meld 3×E = 5 出现数 → public=4 实体）。
  - 集成/Python：`v18_audit_oracle.py` 的合成 supplied 反例与真实 rec2 实体守恒必须转 PASS；
  - 新增 fixture：覆盖 chi（三种形状）、pon、daiminkan、ankan、kakan 与“被鸣牌在河中的下标”跨回合稳定。

### V18-A2：对手 concealed_count 公式与 pending 检测错误

- **等级**：P1。
- **位置**：`current_state_encoding.rs:293-312`（pending_draw_actor）、
  `current_state_encoding.rs:314-325`（concealed_count）。
- **根因**：公式用 `13+pending-2×(chi/pon)-3×daiminkan-4×ankan-1×kakan`，与契约
  （`specs/010/.../contracts/v18-current-state-contract.md` §3.4/§3.9：`13+1(有摸牌)-3×三张副露-4×杠`）
  不一致；且 `pending_draw_actor` 对 pon/chi/kakan/daiminkan/ankan 一律返回 None，未把“当前持有
  第 14 张（被鸣牌进副露 / 岭上牌）”的玩家计入 pending。
  后果：静置状态（已舍牌）下对手暗牌数恒 +1（真实 rec2：编码 11，正确 10）；在 chi/pon 后立即决策点
  与 kakan/杠后岭上（含 chankan 响应窗）又会 -1。
- **最小复现**：rec2 任一决策的 PLAYER rel=2（1 副露、已舍牌，13 张总量）：actual 11、expected 10。
- **影响**：PLAYER 与 OPPONENT_ANALYSIS 的 concealed_count 系统性错误，影响暗牌数/副露约束的可信度。
- **修复方案（公式与 pending 必须一起改）**：
  1. `concealed_count` 改为 `13 + pending - 3×three_melds - 4×kans`（three_melds=Chi/Pon，
     kans=Daiminkan/Ankan/Kakan），与契约一致；
  2. `pending_draw_actor` 改为：
     - `drawn_tile.is_some()` → 观察者自己；
     - 末事件 `tsumo` → actor（持摸牌）；
     - 末事件 `pon`/`chi` → actor（被鸣牌已进副露，总量 14）；
     - 末事件 `daiminkan`/`ankan`/`kakan` → actor（已摸岭上，总量 14；供 chankan 响应窗与杠后决策用）；
     - 末事件 `dahai` → None（弃牌者 13，响应窗内各家 13）；
     - 其余 → None。
     注意保持“只使用公开可见信息”的边界：这些都由 events 增量（公开）推导，合法。
  3. 若该语义在“观察者自身的观察发生在 pon 之后”与“其他家观察同一时刻”之间有差异，
     以真实 replay 的逐决策断言为准（在 oracle 中逐决策核对 total = 13 + pending）。
- **回归测试**：
  - 全决策独立 oracle：`v18_audit_oracle.py` 的 conceald 检查必须 0 失败（在 12 个真实 kyoku 上）；
  - 新增合成用例：chi 后立即决策、pon 后立即决策、daiminkan/ankan/kakan 后（含他人视角 chankan 窗口）；
  - Rust 单测覆盖 5 种副露类型 ×（有摸牌/静置）组合。

### V18-A4：Action Query 丢失 action_id / consume / 赤牌身份 → 不可区分

- **等级**：P1（违反 FR-14）。
- **位置**：`riichi_ppo_v1/model/current_state.py:54-67`（_action_row）、
  `model/encoding_protocol.py:365-383`（_action_fields）、
  `specs/010/.../contracts/v18-current-state-contract.md` §3.10。
- **根因**：32 宽 action token 只有 4 个 metadata（type/primary/source/tsumogiri）+ 10 个 answer，
  action_id 与完整 consume 组合只存在于 15 宽 `query_rows`（仅离线校验）与最终 scatter，
  **不进入 token embedding**。真实回放 826 个多动作决策中 12 个决策的两条不同 chi（不同 consume）
  的 O/D 特征完全相同（如 rec0 seat3 step13 ids=(122,130)，cons=[96,100] vs [88,96]），固定权重下
  raw logits 仅差 ~1e-3。
- **影响**：模型无法从输入区分不同 consume/赤牌/action ID 的合法动作，policy 在碰撞对上是不可学习的。
- **修复方案**：
  1. `CATEGORY_SCHEMAS` 的 `ACTION_OFFENSE_QUERY`/`ACTION_DEFENSE_QUERY` 增加离散字段
     `action_id`（基数 241，0..240），放在 answer 之前或之后（必须在 `_action_fields` 中固定顺序）；
     `_action_row` 从 `row[QUERY_ROW_ACTION_ID]` 写入该字段；
     `semantic_validation.py:251-262` 的 expected 元组与 `current_state.py` 同步；
  2. 由此 241 空间的 action_id 唯一编码（discard：牌种+赤五+tsumogiri；chi：consume 对；
     pon：红/普通对；kan：牌种；hora/ryukyoku/pass/reach），不需要再单独塞 consume 数组；
     但需在文档中明确“action_id 即完整 consume+赤牌身份的规范编码”；
  3. 契约束（§3.10）相应改写：删除“action_id 不进入 embedding”的表述，改为“action_id 进入
     embedding（241 维专用表），query_rows 保留 15 宽原始元数据供校验”；
  4. 契约 payload（`sft/contract.py:44-74`）自动因 schema 变化更新 SHA256；manifest/旧 shard
     视为不兼容（fail closed，无迁移）；
  5. 参数统计与 `parameter_count.py`、README/PROGRESS 的参数量数字同步更新（新增 1 张
     241×dense_slot_dim 表 ≈ 7.7k 参数，总计约 5.764M，仍 ≤6.0M）。
- **回归测试**：
  - `v18_audit_oracle.py` §4 的 exact_collisions 必须为 0（同一决策不同 action_id 的 O/D 特征必须不同）；
  - 新增单元测试：红五 vs 普通五 discard、多种 chi/pon consume 组合、ankan/kakan/daiminkan 的
    action_id 嵌入均不同；
  - 更新协议/schema/hash 相关测试的期望；
  - 验证 `query_rows` 与 actor 行 action_id 一致性、legal_mask 集合、target 映射不变。
